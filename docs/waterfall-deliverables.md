# ウォーターフォール型システム開発 成果物（アウトプット）一覧

本書は次の4部構成で、成果物を「並べる」だけでなく「実際に運用できる形」まで落とし込む。

- 第1部：フル版一覧（最大集合カタログ）
- 第2部：汎用性の検証（どんな案件にも耐えうるか）
- 第3部：ミニマム版（最小構成への絞り込み）
- 第4部：漏れの再検討と最終形（3層テーラリングモデル）

## 第2部：汎用性の検証 ―「どんな案件にも耐えうるか」

### 結論：耐えられない。ただし「カタログ」としては有効。

フル版はあくまで **最大集合（テーラリング元）** であり、そのまま適用すると次の破綻が起きる。

### ① 規模に対して過剰／過少

- 数人月〜十数人月の案件にフル適用すると、**総工数の30〜40%がドキュメント作成に消える**。
- 逆に数百人月規模では、この粒度では足りない（サブシステム別の設計書分冊、体制間の責任分界表などが別途必要）。

### ② 開発対象の種類を吸収できない

フル版は暗黙に「スクラッチ開発のWebシステム」を前提にしている。以下では成果物の骨格ごと変わる。

| 開発対象 | フル版が合わない点 | 必要な代替成果物 |
|---|---|---|
| パッケージ導入（ERP等） | 「詳細設計書」がほぼ存在しない | Fit&Gap分析書、パラメータ設定定義書、アドオン一覧 |
| SaaS設定型（SFA/CRM等） | 設計＝設定であり実装工程が薄い | 設定定義書、オブジェクト／項目定義書、自動化（ワークフロー）設計書 |
| データ基盤・BI | 画面設計より変換ロジックが主 | データフロー定義、ETL仕様、データマート定義、データ品質ルール |
| 組込み・制御 | Web前提の画面／DB設計が不要 | ハードウェアIF仕様、タイミング設計、機能安全文書 |
| AI／機械学習 | 「仕様＝決定論的」の前提が崩れる | 学習データ仕様、精度評価基準、モデル運用（再学習）設計 |
| 既存システム刷新 | As-Is資料が存在しないことが多い | 現行リバース調査書、現新比較テスト仕様 |

### ③ 業界規制・制度要件を吸収できない

| 領域 | 追加で法的・制度的に必須となる成果物 |
|---|---|
| 金融 | FISC安全対策基準対応状況、監督官庁向け説明資料 |
| 医療・製薬 | CSV（コンピュータ化システムバリデーション）関連文書一式（URS/FS/DS/IQ/OQ/PQ）、GxP対応記録 |
| 公共・官公庁 | 政府情報システム標準ガイドライン準拠文書、指定様式の各種計画書 |
| 上場企業の基幹系 | J-SOX（ITGC）証跡：アクセス権限承認記録、変更管理承認記録、開発と運用の職務分離の証明 |
| 製造・車載 | 機能安全（ISO 26262 / IEC 61508）関連文書 |
| 個人情報を大量に扱う | PIA（プライバシー影響評価）、保持・削除ポリシー、越境移転対応 |

### ④ 契約形態・体制を吸収できない

- **請負**：成果物＝検収対象なので、成果物一覧と完成定義が契約の一部になる（削れない）。
- **準委任**：成果物より作業報告が重要になり、一覧の重みが変わる。
- **マルチベンダー**：責任分界点定義書、IF責任表、統合テスト統括計画が追加で必須。
- **オフショア**：詳細設計書の記述粒度を上げないと破綻する（内製なら口頭補完で削れる）。
- **内製**：ソースコードとチケットが実質の設計書として機能し、文書を大幅に削れる。

### ⑤ 一覧そのものの構造的な弱点

| 弱点 | 内容 |
|---|---|
| 粒度が定義されていない | 「基本設計書を作る」は決まっても「どこまで書くか」が決まらない。**事故の主因は一覧の抜けではなく粒度のばらつき**。 |
| 承認者が定義されていない | 誰がレビューし誰が承認するか（RACI）がないと、成果物が「作っただけ」になる。 |
| 維持コストが考慮されていない | 保守フェーズで更新されない文書は、存在することで逆に害になる（誤った前提の温床）。 |
| 「要件凍結」の前提が現実と乖離 | 実際には必ず変更が出る。変更管理プロセスがなければ一覧は機能しない。 |

### 判定

> フル版一覧は「**網羅性のチェックリスト**」としては全案件に有効。
> しかし「**実行計画**」としてはどの案件にも合わない。
> 汎用化には **①必須／②案件条件で発火／③任意** の3層テーラリングが不可欠。

## 第3部：ミニマム版 ― 最小構成への絞り込み

### 削除／統合の判断基準

以下のいずれかに該当するものだけを残す。

- (a) **後工程が作れなくなる**（設計の入力になる）
- (b) **検収・責任分界が成立しない**（契約・合意の証跡）
- (c) **運用・保守が回らない**（引き渡し後に必要）
- (d) **法的・制度的に必要**

逆に、他文書と内容が重複するもの、ソースコードで代替可能なものは統合・削除する。

### ミニマム版：コア12 ＋ 横断3 ＝ 15成果物

| M-1 | プロジェクト計画書 | 体制図・WBS・スケジュール・前提／制約 | (b) 見積と契約の基準線 |
| M-2 | **要件定義書** | 業務要件・To-Be業務フロー・機能一覧・**非機能要件（数値）**・**スコープ外リスト** | (a)(b) すべての起点 |

| 画面・帳票・バッチ・IF設計書（4種） | → M-3 に章立てで内包 |
| 詳細設計書（全機能分） | → 削除。M-5（複雑部のみ）＋ソースコードで代替 |

| EVM・進捗報告書 | → 削除（定例の週次報告で代替） |

### ミニマム版の適用条件（これを外すと破綻する）

- 規模：おおむね **〜30人月／期間6ヶ月以内**
- 体制：**単一ベンダー**、発注者と開発者が近接（オフショア無し）
- 業種：**規制業種でない**（金融・医療・公共・上場基幹系は不可）
- 対象：スクラッチまたは小規模改修、外部連携が少数
- 保守：**開発チームがそのまま保守する**（別ベンダー引継ぎが無い）

## 第4部：漏れの再検討

ミニマム版（15点）を「実案件で本当に事故らないか」で再点検した結果、**15点の一覧としては漏れていないが、各文書の"中身"として抜けやすい論点**が多数見つかった。加えて **2点は文書として追加が必要**と判断した。

### A. 一覧には現れないが、抜けると事故る「章レベル」の漏れ

| # | 漏れやすい論点 | 起きる事故 | 対処（どの文書に内包するか） |
|---|---|---|---|
| ① | 非機能要件の**数値化**（応答時間、同時接続数、データ量、保持期間、RTO／RPO、稼働時間帯） | 受入テストで「遅い」と言われ、基準が無いため無限に揉める | M-2 に必須章として明記 |
| ② | **スコープ外リスト**（やらないことの明文化） | スコープクリープ、無償対応の常態化 | M-2 に必須章 |
| ③ | **権限マトリクス**（誰が何を見られる／操作できる） | リリース直前に権限要件が噴出し、設計からやり直し | M-3 に必須章 |
| ④ | **監視・ログ設計**（何を、どこに、どれだけ残すか） | 障害時に原因が追えない。監査で証跡が出せない | M-3 に必須章 |
| ⑤ | **データ移行リハーサル・現新比較・切戻し判断基準** | カットオーバー当日に破綻し、戻ることもできない | M-9／M-10 に必須章 |
| ⑥ | **外部連携先の調整スケジュール**（相手方の都合＝自社で制御不能） | 連携テストが出来ずスケジュール全崩れ | M-1 のスケジュールに相手方タスクとして明示 |
| ⑦ | **テストデータの個人情報マスキング方針** | 本番データをテスト環境にコピーし、法令違反・情報漏洩 | M-6 に必須章 |
| ⑧ | **教育・トレーニング** | システムは完成したが現場が使えず、業務が止まる | M-11 に研修資料として内包 |
| ⑨ | **承認フロー（誰がいつ承認したか）** | 責任分界が証明できない。J-SOX等で指摘 | M-C（議事録・決定事項ログ）で証跡化 |
| ⑩ | **文書の版管理ルール** | 「どれが最新か分からない」→ 誤った仕様で実装 | M-1 に構成管理の章 |

### B. 文書として追加すべきもの（+2点）

| # | 追加成果物 | 追加理由 |
|---|---|---|
| **M-13** | **環境・調達チェックリスト**（サーバ／回線、ドメイン、SSL証明書、SaaSライセンス、アカウント発行、外部API利用申請） | **リードタイムが最大の落とし穴**。設計も実装も終わっているのに証明書が間に合わずリリース延期、という事故が実際に多い。どの工程文書にも属さないため独立させる |

### D. 汎用化のための最終構造：3層テーラリングモデル

ミニマム17点を **Core** とし、案件条件に応じて自動的に追加する **Conditional** を定義することで、
「ミニマムでありながらどの案件にも耐える」構造になる。

#### Layer 1：Core（17点）＝ 無条件で作る

#### Layer 2：Conditional ＝ 発火条件で追加する

| 発火条件 | 追加する成果物 |
|---|---|
| 規制業種（金融／医療／公共／上場基幹系） | 規制対応文書一式（FISC対応、CSV文書、標準ガイドライン準拠文書、ITGC証跡） |
| パッケージ／SaaS導入 | Fit&Gap分析書、パラメータ設定定義書、アドオン一覧 |
| 既存システム刷新 | 現行リバース調査書、現新比較テスト仕様書 |
| マルチベンダー | 責任分界点定義書、IF責任表、統合テスト統括計画 |
| オフショア／大規模体制 | 全機能分の詳細設計書、用語集・翻訳ルール、コーディング規約 |
| 100人月超 | EVM進捗管理、品質指標管理、構成管理計画（独立）、ステコミ資料 |
| BtoC／インターネット公開 | 脆弱性診断報告書、負荷テスト報告書、可用性設計書、プライバシーポリシー |
| 個人情報を大量に扱う | PIA（プライバシー影響評価）、データ保持・削除ポリシー |
| 24時間365日稼働 | 障害試験報告書、監視設計書、オンコール体制、SLA |
| 外部連携が多数 | IF一覧・IF仕様書・連携テスト計画（相手方調整含む） |
| 保守が別ベンダー | 運用引継ぎ計画、詳細設計書の整備、移管テスト |
| 大量データ移行 | 移行方式設計書、クレンジング仕様、複数回リハーサル計画 |

#### Layer 3：Optional ＝ 余力があれば作る

CRUD図、静的解析レポート、コードレビュー記録、EVM、バグ収束曲線、完了報告書、振り返り記録

## 補足：一覧より重要な3つの運用ルール

成果物一覧が機能するかどうかは、一覧の網羅性よりも次の3点で決まる。

1. **粒度とテンプレートを着手前に確定する**
   「基本設計書を作る」ではなく「基本設計書のテンプレートはこれ」まで決める。事故の主因は抜けではなくばらつき。

2. **成果物ごとに承認者（RACI）を決める**
   作成者・レビュー者・承認者が決まっていない成果物は、作られても合意にならない。

3. **変更管理プロセスを最初から回す**
   ウォーターフォールでも要件は必ず変わる。「変更を止める」のではなく「変更を記録し、影響を見積り、承認を取る」仕組みが、実質的にプロジェクトの成否を決める。
