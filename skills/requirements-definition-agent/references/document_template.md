# 要件定義書の章立てと書き方

Step 7 で使う。`scripts/generate_requirements_docx.py` はこの章立てで出力する。
ここでは「各章に何を書くか／何を書いてはいけないか」を示す。

---

## 章立て

```
1. はじめに
   1.1 本書の目的
   1.2 対象読者と位置づけ
   1.3 用語定義
   1.4 参照した情報源
2. システム化の背景と目的
3. 業務要件
4. 機能要件
   4.1 機能一覧
   4.2 機能詳細
5. 非機能要件
6. 制約・前提条件
7. スコープ外
8. 確認事項（未確定事項）
9. 改訂履歴
```

---

## 各章の書き方

### 1. はじめに

本書が**何を確定させ、何を確定させないか**を最初に書く。要件定義書は設計書ではないので、
「画面の具体的なレイアウトや処理方式は基本設計で確定する」と明記しておくと、後で
「そこまで書いてあると思った」という齟齬を防げる。

`1.4 参照した情報源` には、どの会議・どの資料から要件を起こしたかを日付付きで列挙する。
これがあると、要件の根拠を辿れるようになり、変更管理のときに議論が早い。

### 2. システム化の背景と目的

「何のために作るか」を業務の言葉で書く。ここが曖昧なままだと、後で優先度の判断ができない。
スコープを削る局面で、拠り所になるのはこの章だけである。

書くべきこと: 現状の課題 → 課題による影響（数値があれば必ず入れる）→ システム化で目指す状態。

### 3. 業務要件

**誰が、どの業務で、何を達成したいか**を書く。機能の話はここでは書かない。
業務フロー（As-Is / To-Be）があれば添付する。無い場合でも、対象業務の一覧と
関係者（ロール）の一覧は最低限必要になる。

各要件に ID（BR-xxx）と優先度（Must/Should/Could/Won't）と根拠（source）を持たせる。

### 4. 機能要件

`4.1 機能一覧` は表。大分類／中分類／機能名／概要／アクター／優先度／関連業務要件ID。
この表がそのまま見積・WBS・テストケースの単位になるため、粒度を揃えることが最も重要。

`4.2 機能詳細` は、Must の機能について、入力・処理・出力・例外を数行で書く。
**画面レイアウトは書かない**（基本設計の領域）。ただし画面に載る項目が業務上重要な場合は、
主要項目だけ列挙してよい。

### 5. 非機能要件

6分類（可用性／性能・拡張性／運用・保守性／移行性／セキュリティ／システム環境）ごとに表。
**数値と、その数値が成立する条件をセットで書く**。

未確定の項目も必ず行として残し、「未確定」と明記して確認事項のIDを併記する。
削除してはいけない。行が無いものは、誰も気づかないまま設計・テストを通過してしまう。

### 6. 制約・前提条件

- **制約**: 動かせない条件（予算、期限、既存システム、法令、社内規程）
- **前提**: 現時点でそうだと仮定していること（体制、他システムの改修予定、データ品質）

前提には必ず「**崩れた場合の影響**」を書く。前提が崩れたときに再見積・再スケジュールを
申し入れる根拠になるのは、この記述だけである。

### 7. スコープ外

「今回やらないこと」を明示する。各行に理由を添える。
理由は「予算の都合」「フェーズ2で実施」「業務運用でカバー」など。

**未確認のものは `未確認` と明記する。** 「やらないと合意した」ものと「聞けていない」ものを
同じ表に混ぜたまま区別しないと、後で必ず揉める。

### 8. 確認事項（未確定事項）

未回答のQを一覧にする。列は: ID／確認先／確認内容／背景・理由／関連要件／期限／状態。

この章は**要件定義書の中で最も実務価値が高い**。読み手が次に何をすればよいかが
ここだけに書かれている。件数が多いことを恥じる必要はない。むしろ、確認事項がゼロの
要件定義書は「曖昧さを見落としている」と考えたほうがよい。

### 9. 改訂履歴

版数／日付／改訂内容／作成者／承認者。承認者の欄を空けておくこと自体に意味がある
（誰の承認を取るべきかが見える）。

---

## 全体を通しての原則

- **書けないことは「未確定」と書く。** 空欄にしない。空欄は見落としと区別がつかない。
- **推測で埋めない。** 埋めるなら「仮置き」と明記する。
- **根拠（source）を残す。** 半年後に「なぜこの要件があるのか」を説明できるようにする。
- **合否を判定できない記述を残さない。** 判定できないものは確認事項に移す。
