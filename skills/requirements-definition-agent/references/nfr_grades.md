# 非機能要件チェックリスト（IPA 非機能要求グレード 6分類ベース）

Step 4 で使う。**各項目について「数値になっているか」だけを見る。**
数値が無いものは `status: 未確定` として行を残し、対応する Q を必ず起こす。

判定の基準はひとつ。**受入テストで合否を判定できるか**。
「速いこと」「安定していること」は判定できないので要件ではない。

---

## ① 可用性（Availability）

| 確認項目 | 数値化の単位 | 数値が無いときのQ例 |
|---|---|---|
| 稼働時間帯 | 平日9-18時 / 24時間365日 | 「システムを止めてよい時間帯はありますか（夜間バッチ・メンテ枠）」 |
| 稼働率目標 | 99.5% / 99.9%（月間） | 「年間の許容停止時間は何時間までですか」 |
| 計画停止 | 月◯回 / ◯時間まで | 「月次メンテナンスで停止してよい頻度と時間は」 |
| 目標復旧時間（RTO） | ◯時間以内 | 「障害時、何時間以内に復旧すれば業務が回りますか」 |
| 目標復旧地点（RPO） | ◯時間前の状態まで | 「障害時、何時間前までのデータ消失なら許容できますか」 |
| 縮退運転 | 一部機能のみ継続 等 | 「全面停止と一部機能停止、どちらが業務影響が小さいですか」 |
| 災害対策 | DR拠点の有無・切替時間 | 「被災時の事業継続要件はありますか」 |

**よくある落とし穴**: 「基本的に24時間動いてほしい」＝要件ではない。バックアップ・
パッチ適用・バッチ実行の時間帯が確保できるかを必ず詰める。

---

## ② 性能・拡張性（Performance / Scalability）

| 確認項目 | 数値化の単位 | 数値が無いときのQ例 |
|---|---|---|
| オンライン応答時間 | ◯秒以内（95%tile・条件付き） | 「画面表示は何秒以内なら業務上問題ないですか」 |
| バッチ処理時間 | ◯時間以内（◯件処理時） | 「夜間バッチは何時までに終わる必要がありますか」 |
| 帳票・出力時間 | ◯秒／◯件 | 「帳票出力は何件をどれくらいで出す想定ですか」 |
| 同時接続ユーザ数 | ピーク◯人 / 平常◯人 | 「同時に使う最大人数は何人ですか」 |
| データ量（初期） | ◯万件 | 「稼働開始時に何件のデータが入りますか」 |
| データ量（増加） | 年間◯万件増 | 「年間どれくらい増えますか」 |
| 保存期間 | ◯年 | 「データは何年保存する必要がありますか（法定要件の有無）」 |
| 将来拡張 | ◯年後に◯倍 | 「何年先まで作り替えずに使う想定ですか」 |

**必ず条件を添える**。「3秒以内」ではなく「3秒以内（同時100ユーザ・10万件データ時・95%tile）」。
条件のない数値は、負荷が変われば守れないので合否判定に使えない。

---

## ③ 運用・保守性（Operability / Maintainability）

| 確認項目 | 数値化の単位 | 数値が無いときのQ例 |
|---|---|---|
| 運用時間・体制 | 平日日中 / 24時間有人 | 「誰がどの時間帯で運用しますか（自社／ベンダー）」 |
| 監視対象・方式 | 死活/リソース/業務ログ | 「異常をどう検知しますか。通知先はどこですか」 |
| ログ取得範囲・保持 | 操作ログ◯年、エラーログ◯年 | 「操作履歴はどこまで残す必要がありますか（監査要件）」 |
| バックアップ | 日次フル／世代◯ | 「バックアップの頻度と保持世代数は」 |
| リストア確認 | 年◯回のリハーサル | 「復旧手順の訓練は行いますか」 |
| 障害通知・エスカレーション | ◯分以内に一次連絡 | 「障害時の連絡ルートと時間目標は」 |
| 定期メンテナンス | 頻度・作業窓 | 「OS/ミドルのパッチ適用はどう回しますか」 |
| 保守体制 | 開発と同一／別ベンダー | 「保守は誰が担当しますか」※別ベンダーなら引継ぎ資料が追加で必要 |

**よくある落とし穴**: ログ設計は稼働後に「追えない」と分かる。何を残すかは要件定義で決める。

---

## ④ 移行性（Migration）

| 確認項目 | 数値化の単位 | 数値が無いときのQ例 |
|---|---|---|
| 移行対象データ | 対象テーブル・件数 | 「現行のどのデータを、何件移しますか」 |
| 移行方式 | 一括 / 段階 / 並行稼働 | 「一斉切替と段階移行、どちらを想定していますか」 |
| 移行可能停止時間 | ◯時間（◯曜日の◯時〜） | 「切替のために業務を止められる時間は何時間ですか」 |
| データクレンジング | 誰が・いつまでに | 「現行データの名寄せ・不備修正は誰が行いますか」 |
| 移行リハーサル | ◯回実施 | 「本番前に何回リハーサルを行いますか」 |
| 現新比較 | 対象・判定基準 | 「移行結果の正しさは何をもって確認しますか」 |
| 切り戻し | 判断期限・手順 | 「切替失敗時、いつまでに戻す判断をしますか」 |
| 業務移行・教育 | 対象人数・時間 | 「利用者は何人で、いつ教育しますか」 |

**よくある落とし穴**: 移行は要件定義で扱われず、直前に破綻する。**停止可能時間と
切り戻し判断期限**は、要件定義の段階で押さえておく。

## ⑤ セキュリティ（Security）

| 確認項目 | 数値化の単位 | 数値が無いときのQ例 |
|---|---|---|
| 認証方式 | ID/PW, MFA, SSO(SAML/OIDC) | 「ログイン方式の指定はありますか（既存SSO利用の要否）」 |
| パスワードポリシー | 桁数・有効期限・履歴 | 「社内規程のパスワード要件はありますか」 |
| 権限管理 | ロール数・権限マトリクス | 「誰がどのデータを見られる／編集できますか」 |
| データ暗号化 | 通信(TLS)・保存時 | 「保存データの暗号化要件はありますか」 |
| 個人情報・機微情報 | 対象項目・取扱ルール | 「個人情報はどの項目が該当しますか。越境移転はありますか」 |
| 監査ログ | 対象操作・保持年数 | 「誰がいつ何をしたかの記録は、どこまで必要ですか」 |
| アクセス制限 | IP制限・VPN・端末制限 | 「社外からのアクセスを許可しますか」 |
| 脆弱性対応 | 診断の要否・頻度 | 「リリース前の脆弱性診断は実施しますか」 |
| 準拠すべき基準 | ISMS/PMS/FISC/GxP等 | 「準拠が必要な社内規程・業界基準はありますか」 |

**権限マトリクスは後付けできない**。ロール×機能×CRUD の表が要件定義で埋まらない場合、
必ずQに落とす。リリース直前に権限要件が出ると設計からやり直しになる。

---

## ⑥ システム環境・エコロジー（Environment）

| 確認項目 | 数値化の単位 | 数値が無いときのQ例 |
|---|---|---|
| 稼働環境 | クラウド(AWS/Azure/GCP)/オンプレ | 「インフラの指定はありますか」 |
| 利用ブラウザ・OS | Chrome最新, Windows11 等 | 「利用者の端末環境（OS・ブラウザ・バージョン）は」 |
| モバイル対応 | スマホ/タブレットの要否 | 「外出先や現場から使いますか」 |
| ネットワーク | 回線帯域・社内/社外 | 「拠点からの回線条件に制約はありますか」 |
| 外部連携先 | システム名・方式・頻度 | 「連携する外部システムと、その窓口担当は」 |
| ライセンス | 種別・本数・調達期限 | 「必要なライセンスは誰がいつ調達しますか」 |
| 印刷・帳票 | プリンタ・用紙・様式 | 「印刷要件（専用用紙・プリンタ機種）はありますか」 |

**よくある落とし穴**: SSL証明書・ドメイン・SaaSライセンス・アカウント発行は
**調達リードタイム**が読めず、設計も実装も終わっているのにリリースできない事故を起こす。
要件定義の時点で期限を確認事項として立てておく。

## 出力時の書式

`non_functional_requirements` の1行は次の形にする。

```json
{
  "id": "NFR-001",
  "category": "性能・拡張性",
  "item": "オンライン応答時間",
  "value": "3秒以内（95%tile / 同時100ユーザ・データ10万件時）",
  "basis": "現行システムの体感が遅いとの指摘（10/3 ヒアリング 田中様）",
  "status": "確定",
  "question_id": ""
}
```

未確定の場合は `value` を空にせず `"未確定"` と書き、`question_id` に対応するQのIDを入れる。
空欄は「見落とし」と区別がつかないため、必ず明示的に埋めること。
