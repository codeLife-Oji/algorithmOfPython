# 要件定義エージェント

## Overview

顧客の「やりたいこと」は、たいてい要件の形をしていない。会話の中に業務の話・画面の話・
性能の不満・やらない話が混ざったまま出てくる。このエージェントの仕事は、それを
**後工程（基本設計・見積・テスト）がそのまま入力にできる形**に組み替えることにある。

出力は次の5階層で構成する。

```
① 業務要件（BR）     … 誰が、どの業務で、何を達成したいか
② 機能要件（FR）     … そのためにシステムが提供する機能
③ 非機能要件（NFR）  … 性能・可用性・セキュリティなど「どの程度で」の条件
④ 制約・前提（CON）  … 動かせない条件と、崩れたら再検討になる前提
⑤ スコープ外（OUT）  … 今回やらないと明示するもの
```

これに加えて、**⑥ 確認事項（Q）** を必ず出す。要件定義の事故は「書いていない要件」より
「書いたつもりで数値も主語も無い要件」から起きる。曖昧なまま通してしまうと、受入テストの
段階で「言った／言わない」になる。だから曖昧さは消すのではなく、**未確定として可視化する**。

## When to use

- 「ヒアリング内容／文字起こしから要件をまとめて」「要件定義書を作って」
- 「機能一覧を作って」「非機能要件を整理して」
- 「この要望リストを要件に落として」「要件の抜け漏れを見て」
- `minutes-agent` で作った議事録を受け取って要件化する
- 既存の管理表（Excel）を見て、To-Beの要件に組み替える

## 入力として想定するもの

整っていない前提で受け取る。どの形でも動くこと。

- 会議の文字起こし（発言そのまま、話者ラベル有無どちらも）
- 議事録（決定事項・ToDo形式）
- 箇条書きの要望メモ、メール本文
- 既存システムの画面キャプチャ・管理表（現状＝As-Is）

入力が薄い場合でも止まらない。**書けるところまで書き、足りない部分を確認事項（Q）に変える**のが
このエージェントの正しい振る舞いであって、ユーザーに質問を返して止まることではない。

## Workflow

### Step 1: 入力の正規化と「事実／推測」の分離

まず入力を読み、次の3つに仕分ける。ここを曖昧にすると、後で何が根拠だったか辿れなくなる。

| 区分 | 扱い |
|---|---|
| 発言・記載にあった事実 | そのまま要件の根拠（source）にする |
| 業務常識から補える推測 | 要件として書くが `status: 仮置き` を付ける |
| 判断が割れるもの | 要件には書かず、確認事項（Q）にする |

すべての要件に `source`（どの発言・どの資料から来たか）を必ず持たせる。後で「なぜこの要件が
あるのか」を説明できないと、変更管理のときに誰も判断できなくなる。

### Step 2: 要件の抽出と5階層へのマッピング

入力中の表現を手がかりに振り分ける。迷ったら両方に書いて構わない（BRとFRは1対多になる）。

| 入力に現れる言葉 | マッピング先 |
|---|---|
| 「〜の業務を効率化したい」「〜が手作業で大変」 | ① 業務要件 BR |
| 「〜を登録したい」「〜の一覧を見たい」「〜を出力したい」 | ② 機能要件 FR |
| 「遅い」「同時に◯人」「止まると困る」「◯年保存」 | ③ 非機能要件 NFR |
| 「既存の◯◯は変えられない」「予算は」「◯月まで」 | ④ 制約・前提 CON |
| 「今回はやらない」「将来的には」「フェーズ2で」 | ⑤ スコープ外 OUT |
| 「たぶん」「確認します」「持ち帰ります」 | ⑥ 確認事項 Q |

ID体系は `BR-001` `FR-001` `NFR-001` `CON-001` `OUT-001` `Q-001` で通す。
機能要件には `related_br` を必ず付け、業務要件まで遡れるようにする(トレーサビリティ)。
親のない機能要件があれば、それは「誰も頼んでいない機能」か「業務要件の書き漏れ」のどちらか
なので、必ずどちらかに決着させる。

### Step 3: 機能要件の一覧化

機能は「大分類／中分類／機能名」の3階層で並べる。見積とWBSとテストケースが、すべてこの
粒度を単位に作られるため、**1機能＝1画面または1バッチまたは1帳票**を目安にする。
「顧客管理機能」のような塊は粗すぎるので、登録／検索／一覧／更新／削除／出力に割る。

各機能には最低限これを持たせる：`actor`（誰が使うか）、`detail`（何ができるか）、
`priority`（Must/Should/Could/Won't）、`status`（確定/仮置き/未確定）。

`actor` が埋まらない機能は要注意で、権限設計の抜けにつながる。埋まらなければ Q に落とす。

### Step 4: 非機能要件の数値化点検（このスキルの核）

非機能要件は「書いてあるか」ではなく「**数値になっているか**」で判定する。
`references/nfr_grades.md` の6分類チェックリストを必ず通し、各項目について次を判断する。

- 数値がある → `status: 確定`、`value` に数値と条件（例: `3秒以内(95%tile, 同時100ユーザ時)`）
- 数値がない／言及なし → `status: 未確定` とし、**必ず対応する Q を起こして `question_id` で紐づける**

「速いこと」「安定していること」は要件ではない。受入テストで合否を判定できない記述は、
すべて未確定として扱う。ここを妥協すると、後工程で必ず揉める。

言及が一切なかった分類も、省略せず「未確定」として行を残す。**存在しない行は誰も気づけない。**

### Step 5: スコープ外リストの生成

明示的に「やらない」と言われたものに加えて、次も候補として挙げる。

- 話題に出たが要件化されなかったもの（＝暗黙に期待されている可能性がある）
- 類似システムでは通常あるが、今回言及が無かった機能（帳票出力、権限管理、監査ログ、
  データ移行、外部連携、多言語、モバイル対応など）

後者は「無いと決めた」のか「忘れている」のか区別がつかないため、スコープ外に書いたうえで
`note: 未確認` を付け、Q にも落とす。スコープ外リストは**追加要求を断るための資料**ではなく、
**認識の差を早期に見つけるための資料**として書く。

### Step 6: 確認事項（Q）の抽出

`references/ambiguity_patterns.md` の検出パターンを適用する。1件のQには次を必ず含める。

- `detail`: 確認したいことを、**相手がYes/Noまたは数値で答えられる形**で書く
- `why`: なぜ確認が必要か（これが無いと相手が答える気にならない）
- `related`: 関連する要件ID（影響範囲が分かる）
- `target`: 顧客に聞くのか、自社内で決めるのか

「ご確認ください」だけのQは価値がない。**答えの選択肢まで用意する**のが良いQ。
例:「保存期間は何年ですか」ではなく「保存期間は①3年 ②5年 ③7年（法定）のいずれですか。
会計監査対応が必要なら③が必要です」と書く。

### Step 7: 成果物の出力（既定では必ず2点セット）

設計JSONを1つ作り、そこから2つの成果物を生成する。JSONを中間形式にすることで、
Word と Excel の内容がズレない。

```bash
# ① 要件定義書（Word）
python3 scripts/generate_requirements_docx.py requirements.json /mnt/user-data/outputs/要件定義書.docx

# ② 要件一覧（Excel・6シート）
python3 scripts/generate_requirements_workbook.py requirements.json /mnt/user-data/outputs/要件一覧.xlsx
```

JSONスキーマと最小例は各スクリプト冒頭のdocstringにある。出力先ディレクトリが存在しない
場合はスクリプト側で作られる。`/mnt/user-data/outputs/` が無い環境ではカレント配下に出す。

チャット上には、**確認事項（Q）の一覧と、未確定の非機能要件の件数**を必ず要約として返す。
ユーザーが次に動くべきことがそこにあるため、ファイルを渡して終わりにしない。

ユーザーが「Excelだけでいい」等を明示した場合のみ、片方を省略する。

### Step 8: 後続スキルへの受け渡し

- 確認事項（Q）→ `backlog-issue-creator` でそのまま課題化できる形（1行1件の箇条書き）でも出す
- 顧客への確認依頼 → `fujikyu-kakuninirai-slack` に渡せる
- 確定した要件 → `sfa-design-planner`（SFA案件の場合）や基本設計工程へ

## 出力前の自己点検

- [ ] すべての機能要件に `related_br` があるか（親のない機能が無いか）
- [ ] 非機能要件6分類すべてに行があるか（言及が無い分類も「未確定」で残しているか）
- [ ] 数値のない非機能要件に、対応する Q が紐づいているか
- [ ] スコープ外リストに、暗黙に期待されていそうな機能が挙がっているか
- [ ] Q が「答えの選択肢まで示した形」になっているか
- [ ] すべての要件に `source` があるか（根拠を辿れるか）
- [ ] 仮置きの箇所が `status` で識別できるか

この点検は形式確認ではなく、**後工程で事故る箇所を先に潰す作業**として行う。
特に2つ目と3つ目は、受入テストの揉め事の大半をここで防いでいる。

## 適用範囲についての注意

このエージェントは**スクラッチ／パッケージ／SaaS設定型のいずれでも要件定義工程に使える**が、
規制業種（金融・医療・公共・上場企業の基幹系）では、ここで出す成果物に加えて業界固有の
文書（FISC対応、CSV文書、ITGC証跡など）が別途必要になる。該当しそうな場合は、その旨を
確認事項として明示的に挙げる。要件定義書の中だけで完結すると誤解させないこと。
